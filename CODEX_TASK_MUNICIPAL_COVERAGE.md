# Task: close the municipal coverage gap for Germany, the USA, Britain and France

You are working in `~/dev/czbudget/website` on `publicspendingdata.org`. The site publishes
municipal budget data for 26 countries. Four are incomplete, and they are incomplete for four
different reasons — read the per-country sections before deciding what to do.

**Do not start by gathering data.** Two of these four already have the data. Check the state
before you fetch anything.

## How this repository models municipal data

Facts live in BigQuery: `czbudget-janrezab.budget_detail.municipal_budget_line_facts`. It is
partitioned on `fiscal_year`, so **every query needs a partition filter** or it is rejected.

```
public_entity_id   STRING  REQUIRED  "<ISO alpha-2>:<national code>", e.g. "DE:05315000"
fiscal_year        INTEGER REQUIRED
fiscal_period      STRING  REQUIRED  "FY", or a slice like "B6" / "FY-2026"
reporting_scope    STRING  REQUIRED  "municipal_general_budget"
budget_stage       STRING  REQUIRED  proposal|enacted|revised|committed|actual|paid|carried_over
budget_side        STRING  REQUIRED  revenue|expenditure|financing
economic_item_code STRING  REQUIRED  the source's own code, not a mapped one
amount_local       NUMERIC REQUIRED  units of currency_code, 6dp as a string
currency_code      STRING  REQUIRED
is_consolidation_item BOOL REQUIRED  a deduction from a gross figure, not a figure
is_financing       BOOL    REQUIRED  funds the budget rather than being it
is_summary_row     BOOL    REQUIRED  a total of other rows in the same table
source_id          STRING  REQUIRED  "<cc>-<publisher>-<series>-<edition>"
```

Three registries sit beside it:

- `data/registry/municipal-entities/<ISO3>.v1.json` — identity only: code, name, region,
  population, currency, page URL. No amounts.
- `data/registry/municipal-item-labels.v1.json` — the source's own label per item code, never
  translated.
- `pipeline/config/municipal_headline_rules.json` — which facts a municipality leads with.

Profiles are generated by `scripts/build-profiles-from-warehouse.mjs` from those three plus the
warehouse. Read it before writing a loader; it is the consumer your data has to satisfy.

## Conventions that are not negotiable

- **Loaders write NDJSON only.** `bq load` is a separate explicit step. See
  `scripts/load-municipal-facts-dnk.py` and `scripts/load-municipal-facts-jpn-estat.py`.
- **Keep the source's own codes and labels.** A translated label cannot be checked against the
  original filing.
- **Keep the source's sign convention** and resolve it at presentation. Denmark books revenue as
  a credit; those rows are stored negative.
- **Mark, do not drop.** Financing, consolidation items and summary rows are marked with the
  booleans above so a consumer can exclude them. Dropping them loses data.
- **Every fetcher is resumable and rate-paced.** Six of Brazil's 88 requests timed out on the
  first pass; the fetcher skips what is cached, so re-running finished the job.
- Pin the gcloud account per invocation — another session on this machine changes the active
  one, and a permission error is often that race, not IAM.

## The acceptance test

A country is publishable when its generated profiles reproduce the figures the site already
publishes, or — where the site publishes none — when the result is internally coherent and
plausible on its own terms.

```
node scripts/build-profiles-from-warehouse.mjs --country DEU --out .warehouse-profiles --verify
```

Fifteen countries pass this against 54,502 published headlines. **Do not publish a country
that does not.** Poland is served on an *authored* rule with no published baseline, admitted
only because its revenue-to-expenditure ratio has a median of 1.001 across 4,956 entity-years —
the shape of a budget that must balance. Ukraine and Sweden were written the same way and
withdrawn: their ratios came out at 0.5 and 0.2, because their revenue series are incomplete.
Publishing them would have shown a Swedish municipality spending five times its income.

## Britain — the data is already loaded. It needs publishing, not gathering.

**State:** 374 authorities, 552,003 line facts, England + Scotland + Wales. Zero published.
Ledger says `not_loaded` / `source_available`, which is now wrong for the fact layer.

Two things make Britain unlike the fifteen that work:

1. **Periods are year-qualified**: `FY-2024`, `FY-2025`, `FY-2026`, out to `FY-2028`. Every
   other country uses `FY`. The headline rule matches on `fiscal_period` exactly, so it will
   match nothing until you decide what a British "year" is.
2. **There is a `financing` budget_side**, not just revenue and expenditure.

Most rows are `enacted` (budgets), with `actual` revenue only for 2024–2025. Decide what a
British authority's headline should be and whether budget and outturn belong in one series.

**Deliverable:** a headline rule, generated profiles, and a ledger row that stops saying
`not_loaded`. No fetching required.

## France — already published. One reconciliation is open.

**State:** 34,744 of 34,875 profiles published, `status=partial`, `availability=loaded`.
10.4M line facts across 35,042 entities. France is fine and is served by its own path
(`server/france-municipal-lines.mjs`).

The open question is only whether France can join the shared generator. It cannot yet:

- Two DGFiP sources cover **different populations** — `fr-dgfip-commune-balances-*` has 31,384
  entities, `fr-dgfip-balances-fonction-*` has 3,493. A test entity in one is absent from the
  other.
- For `FR:01001` in 2025 the warehouse sums to revenue 995,320.87 and expenditure 2,366,440.01,
  while the published figures are 914,157.60 and 2,285,276.74. **Both sides differ by exactly
  81,163.27**, which is the signature of *opérations d'ordre* — internal transfers that appear
  equally on both sides and are excluded from the "réel" budget. No subset of that entity's
  accounts summed to 81,163.27, so it is not a simple account-code exclusion.

**Deliverable:** identify what that 81,163.27 is, mark those rows `is_consolidation_item`, and
show the rule reproducing published figures across a real sample. If it turns out France should
stay on its own path, say so with evidence — that is a valid answer.

## Germany — genuinely needs data. Eleven cities is not a country.

**State:** 11 entities, 1,152,009 facts, all from individual city open-data portals (Aachen,
Bonn, Dortmund and eight more). The directory lists 10,756 municipalities.

Eleven hand-collected cities will not scale to 10,756. Germany is federal and municipal
finance statistics are collected by the *Statistische Ämter des Bundes und der Länder*.

**Start here, not with more city portals:**
- Destatis Genesis-Online, the *Jahresrechnungsstatistik der kommunalen Haushalte* — themes
  around 71xxx. There is a documented REST API.
- The Regionaldatenbank (`regionalstatistik.de`) publishes the same statistics at
  *Gemeinde* level, which is the level this needs.
- Länder statistical offices publish the same collection, sometimes at finer granularity.

Entity codes should be the **Amtlicher Gemeindeschlüssel** (8-digit AGS), so
`DE:05315000` for Köln. Check what the existing directory uses and reconcile.

**Deliverable:** nationwide or Land-by-Land coverage at Gemeinde level, an entity directory
keyed on AGS, a headline rule, and profiles that pass the acceptance test. If nationwide data
is only available at *Kreis* level, say so and load that, clearly labelled — a coarser real
answer beats a finer invented one.

## USA — genuinely needs data. Four cities is not a country.

**State:** 4 entities (NYC, Chicago, Los Angeles, San Francisco), 47,142 facts. The directory
lists 19,401.

**Start here:**
- The Census Bureau **Annual Survey of State and Local Government Finances** is the only
  nationwide source, covering ~90,000 governments with a documented API and a published
  classification manual.
- Its unit of account is a *government*, not a place — counties, municipalities, townships,
  school districts and special districts are separate. Decide which of those this site means
  by "municipality", write the decision down, and be consistent.
- Entity codes should be the Census government ID; reconcile with whatever the directory uses.

Note the survey is a **sample** below a size threshold, with only larger governments
enumerated every year. That is a real limitation to record, not to paper over.

**Deliverable:** nationwide coverage at the chosen level of government, an entity directory, a
headline rule, and profiles that pass. Record the sampling limitation in the ledger row.

## Chain to update when a country becomes published

Adding one country is never a one-file change. In order:

1. `data/registry/municipal-entities/<ISO3>.v1.json`
2. `pipeline/config/municipal_headline_rules.json`
3. `npm run build:municipal-itemized-coverage`
4. `npm run build:data-freshness`
5. `data/methodology-sources.v1.json` — the ledger row, `status` and `source_availability`
6. `node scripts/create-release-manifest.mjs`
7. `node scripts/validate-integrity.mjs --write-report`
8. `node scripts/create-release-manifest.mjs` again — the report is hashed by the manifest, so
   the manifest is built, the report written, and the manifest rebuilt
9. `npm run validate` and `npm run test:api`

**"Published" means what the build ships.** The build hydrates `data/municipal-expansion` from
GCS; `.warehouse-profiles` is gitignored and is *not* in the image. Counting profiles that only
exist locally as published is a real defect — it happened, and it credited Poland with 2,486
profiles that ship nowhere.

## Traps that cost real time here

- `bq --format=json` returns **every column as a string**, booleans included. `is_financing !==
  true` is silently always true and disables the filter without erroring.
- e-Stat ships **Shift-JIS**. Decoding as UTF-8 turns every header into mojibake and the
  failure looks like a missing column.
- Statistical portals often index by **publication year, not fiscal year**. On e-Stat,
  `year=20240` returns FY2023.
- Measure against the **raw source**, not a downstream artifact. Japan's "leaf sums are 2.47x
  published revenue" was measured against a file capped at 360 rows per municipality, and it
  pointed at the wrong cause for weeks.
- When a figure differs by the **same amount on both sides**, look for internal transfers
  before looking for a missing account.
- Record what you cannot close, with numbers, in `pipeline/config/data_layers.json` under
  `known_gaps`. That file is the running record and it is more useful than a clean result.
